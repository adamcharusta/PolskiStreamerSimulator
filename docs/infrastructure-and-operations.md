# Infrastructure and Operations

Status: **architecture proposal with confirmed platform direction**, 2026-10-12. The owner replaced production Docker Compose with Ansible-managed k3s and wants reusable Microsoft SQL Server and HashiCorp Vault services. Docker Compose remains the local-development entry point. `database` and `vault` are confirmed as separate Kubernetes namespaces. `ovh2` stays outside k3s as the backup host. Helm manages both shared services and the game application. No installation on either VPS has been authorized or attempted in this phase.

## Cluster ownership and namespaces

Ansible is the idempotent entry point: inspect the existing host and cluster first, install k3s only when appropriate, apply pinned configuration, then verify each prerequisite before rolling out workloads. Never reinstall or overwrite an existing cluster blindly. Keep inventory, playbooks and roles under `k8s/ansible/`, with Helm charts, assets and environment values for shared services **and the game application** elsewhere in `k8s/`; keep passwords, unseal material and kubeconfig out of Git. GitHub Actions workflows live in `.github/workflows/`. Ansible's `kubernetes.core` collection can manage Kubernetes resources and Helm releases. [Ansible Kubernetes collection](https://docs.ansible.com/projects/ansible/latest/collections/kubernetes/core/docsite/kubernetes_scenarios/k8s_intro.html).

| Namespace | Owner | Workloads and separation |
| --- | --- | --- |
| `kube-system` | k3s | Cluster services, including the packaged Metrics Server if enabled. |
| `database` | shared infrastructure | One private SQL Server instance with persistent storage; separate databases and logins for each project and for staging/production. |
| `vault` | shared infrastructure | HashiCorp Vault, persistent storage, audit logging and tightly scoped authentication policies. |
| `streamer-prod` | game | Production WebApp/API, React static serving and game-specific jobs/configuration. |
| `streamer-staging` | game | Isolated staging app, credentials and database; every passing `develop` push deploys here; entire public origin restricted to invited testers. |
| `streamer-rc` | game | Separate restricted release-candidate app, database and Vault policy for `release/*` validation at `rc.polskistreamersimulator.pl`. |

`default` is not used for shared production services. Namespace separation is an organizational and policy boundary; database logins, Vault policies, Kubernetes RBAC and NetworkPolicies enforce access. Future projects get their own app namespaces and database identities, without sharing the game's credentials. Keep SQL Server and Vault internal to the cluster unless a later requirement justifies exposure. Run k3s on `ovh`; keep `ovh2` outside the cluster as the independent off-host backup destination.

## Ansible and Helm reconciliation

Proposed playbook order for infrastructure changes: read-only host preflight; k3s install/upgrade with a pinned version and explicit rollback plan; cluster health and storage checks; namespaces/RBAC/NetworkPolicies; shared SQL Server and Vault installation; backup/restore checks; application releases; smoke tests. `ansible-playbook --check` and a staging rehearsal precede a production infrastructure change. Pin chart versions and container image digests; apply small, reviewable upgrades rather than an unbounded “latest” install. On every passing `develop` push, `release/*` candidate deployment, or tested `main` PR merge, the app release first runs Ansible conformity checks. Detected drift blocks deployment and triggers a report; repair uses a separate reviewable infrastructure workflow. A push to `main` after a `release/*` or `hotfix/*` merge triggers production automatically after all checks pass; the earlier manual environment gate is superseded.

k3s packages `metrics-server`, Traefik and local-path storage unless disabled; Ansible should **check what is installed** rather than installing a duplicate Metrics Server or ingress controller. Kubernetes HPA is a built-in `autoscaling/v2` resource, not a service installed by Helm. A Helm chart may define an HPA for the stateless WebApp/API. Verify `metrics.k8s.io`, pod CPU/memory requests, and observed HPA status before enabling scaling. Do not apply HPA to SQL Server or Vault. On a single VPS, extra API pods share the same CPU/RAM and provide no host-level availability. [k3s packaged components](https://docs.k3s.io/installation/packaged-components), [Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

## Shared SQL Server

The requested shared SQL Server is **one instance in the `database` namespace**, implemented as a single-replica `StatefulSet` with a PersistentVolumeClaim, a private Service, resource requests/limits, readiness/startup checks and an explicit supported edition/license. A standard multi-replica Deployment or HPA would create separate SQL Server instances, not a replicated database. Microsoft recommends a StatefulSet and one SQL Server instance per pod. Verify host architecture, filesystem, durable-storage path, memory and disk capacity before choosing the version and edition. The existing `ovh` inventory is deferred by the owner; do not infer capacity from the planned topology. [Microsoft SQL Server StatefulSet guidance](https://learn.microsoft.com/en-us/sql/linux/containers/kubernetes-best-practices-statefulsets?view=sql-server-ver17).

Provision distinct databases and least-privilege logins for production, staging and every later project. Run EF Core migrations through a controlled release Job or operator step, never concurrently on every API replica. Preserve the confirmed daily encrypted SQL backups to `ovh2`, 30 daily and 12 monthly copies, restore drills, and approximately 24-hour recovery-point and recovery-time targets. A PVC is not a backup. A future multi-node cluster does not by itself turn a single SQL Server pod into database HA.

## Shared Vault and application secrets

Use the official HashiCorp Vault Helm chart in `vault`; the chart deploys stateful server resources when configured for persistent service. The owner chose **auto-unseal through an external KMS** and **encrypted Vault snapshots on `ovh2` in a separate backup set from SQL Server**. Retain **30 daily and 12 monthly Vault snapshots**, with independent integrity checks and restore drills. No KMS provider has been selected; compare available accounts, ongoing cost and recovery requirements before choosing one. Select the provider, its credential and recovery procedure, Vault storage, audit, TLS, snapshot schedule and restore setup before production. Vault's default standalone file-storage chart mode is explicitly unsuitable for production in HashiCorp guidance; do not treat multiple replicas on one VPS as physical high availability. The infrastructure plan must show how Vault becomes available after a full host loss and how its encrypted snapshots and external KMS access are recovered. The exact Vault setup remains an implementation gate pending VPS inventory; `ovh2` is an external backup host, not a k3s node. [HashiCorp Vault Helm guidance](https://developer.hashicorp.com/vault/docs/deploy/kubernetes/helm/run), [Vault Raft deployment guide](https://developer.hashicorp.com/vault/tutorials/kubernetes/kubernetes-raft-deployment-guide).

Use a dedicated Kubernetes ServiceAccount and Vault policy per environment and workload. The game's API reads only its own database credential and application secrets; staging cannot read production paths. Document bootstrap separately because Vault cannot safely supply the only credentials needed to unlock itself. Never print secrets in Ansible output, Kubernetes events or Serilog. Decide whether Vault Agent injection or another supported integration fits the final chart; avoid putting long-lived plaintext values in committed Helm values files.

## WebApp and release checks

Deploy production, release candidate and staging from tested immutable images. Use separate namespaces, ServiceAccounts, Vault paths, databases, hostnames and ingress rules. Configure HTTPS and the ASP.NET Core forwarded-header trust boundary; test cookie login, TOTP/recovery-code 2FA and redirects through ingress. Create the sole owner account through a **one-time administrative command on the server after database migration**, with no public registration or automatic account seeding from deployment secrets. Do not expose the initial password or TOTP setup secret in command arguments, logs or workflow output. If the API is scaled beyond one replica, persist and share ASP.NET Core Data Protection keys so admin cookies remain valid across pods. Give stateless API pods readiness/liveness/startup probes and resource requests. A dedicated job performs database migrations before the new WebApp version receives traffic.

Keep the existing operations targets: owner-only Discord alerts for failed backups and service outages, daily off-host SQL backups, tested restore, staging and release-candidate checks. A tested `release/*` or `hotfix/*` PR merge into `main` initiates automatic production release if tests, Ansible checks, migrations and rollout health pass. Add checks for k3s node health, Metrics Server/HPA status, SQL PVC capacity, Vault seal state, Vault snapshots and backup transfer. Rehearse a whole-host recovery; restarting pods is insufficient after disk or VPS loss. Apply the confirmed career-data retention sweep after restoring an older backup and before reopening the API (currently a proposed restore procedure pending owner confirmation). **M4-A (TD-121):** the sweep is the WebApp command `retention-sweep` (`dotnet WebApp.dll retention-sweep` in the image), run against the restored database before the API pods start; the API also sweeps at startup and hourly (`Retention:Enabled`, `Retention:Interval`). See [Development and Delivery](development-and-delivery.md) for the workflow and local Compose boundary.

- VPS CPU architecture, RAM, disk, filesystem and existing workloads; SQL Server edition/license and storage class depend on this inventory.
- Release-candidate resource budget, DNS for `rc.polskistreamersimulator.pl`, ingress ownership, TLS certificates, Kubernetes image registry, CI deployment identity and Discord alert destination.
- Initial namespace and Helm chart naming conventions for future projects; shared services and application releases both use Helm.
