## Implementation Defaults to Validate

- Target .NET 10 LTS with Wolverine HTTP endpoints in ASP.NET Core.
- Use both `WolverineFx.Http.FluentValidation` for HTTP requests and `WolverineFx.FluentValidation` for CQRS messages, avoiding duplicate validator registrations. Generate OpenAPI with the ASP.NET Core generator and Wolverine command before Orval runs.
- A service worker may cache static assets for the optional PWA, but game actions require a live connection. Store only anonymous access material and the most recent confirmed display state in the browser; SQL Server owns careers.
- Test the two most recent major desktop versions of each named browser, plus current Android Chrome and current/previous iOS Safari.
- Inspect the existing ingress first. k3s packages Traefik by default; use it unless host inventory or an existing proxy gives a reason to choose another ingress. Keep SQL Server and Vault private.
- Consider SQL Server 2025 Express for the new database instance if VPS capacity and edition limits fit. Use separate staging and production databases/logins in one instance to avoid duplicate database processes on the shared VPS.
- Rehearse SQL Server restores from off-host backups. Give staging a separate namespace, database, Vault path, credentials and domain.
- After restoring an older backup, apply the six-month unfinished and 12-month finished retention rules before reopening public access; test that expired careers do not reappear.
- Issue individual staging tester credentials through a reverse proxy or equivalent access gate; do not reuse game or production administrator credentials. Define the test-data policy before inviting testers.
- Use a private Discord webhook or bot credential for operational alerts; include service, environment, timestamp, and a short error category, but no player data, career secrets, or database credentials.
- Use separate GitHub staging/production environments for scoped credentials and deployment history. Do not configure a required-reviewer gate on production under the latest automatic-release decision; keep staging credentials separate from production.

## Deployment Inputs Still Needed

The game host is `ovh`; the off-host backup destination `ovh2` remains outside k3s. Production, staging and release-candidate domains are `polskistreamersimulator.pl`, `staging.polskistreamersimulator.pl` and `rc.polskistreamersimulator.pl`. A read-only inventory of `ovh` was attempted twice on 2026-10-12, but SSH timed out during banner exchange before authentication; this does not establish whether the VPS itself is down. The user deferred further VPS checks. When resumed, verify connectivity to both hosts, measure CPU, RAM, disk, ports, k3s and ingress state, storage, existing workloads, and backup capacity, then test backup transfer and restore. Confirm DNS management, select the external KMS provider, rehearse Vault recovery, and set the Discord alert destination. The owner is the sole leaderboard moderator with Identity cookie login, TOTP and recovery codes; create the account with a one-time server command and design emergency recovery if those codes are lost. Confirm the privacy notice and telemetry retention before enabling analytics. A local prototype can use a development SQL Server instance; public deployment requires the host inventory. ## Superseded Decisions

The owner's later online-only/C#-Domain choice replaces the earlier offline-play, shared TypeScript simulator, Node replay worker, signed offline starts, local ranked-submission queue, and three ranked starts per day. The owner also replaced the MUI admin UI with Tailwind/shadcn/ui, production Docker Compose with Ansible-managed k3s, and manual approval inside the production workflow with automatic publication from `main`. The brief `master` proposal and direct `develop`→production PR proposal are superseded by Git Flow with `release/*` and `hotfix/*`. Docker Compose remains current for local development. Preserve the other historical choices only in the game-design decision log; do not implement them as current requirements. See [Development and Delivery](development-and-delivery.md).
