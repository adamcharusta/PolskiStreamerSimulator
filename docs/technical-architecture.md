# Technical Architecture and Ranking Integrity

Status: **architecture decisions in progress**, 2026-10-12. The owner chose an online-only game with server-authoritative C# rules, a React/TypeScript client, ASP.NET Core 10 with Wolverine HTTP/CQRS, EF Core/SQL Server, and an owner-only admin route. Ansible-managed k3s with shared SQL Server and Vault replaces the earlier Docker Compose deployment; the older offline TypeScript simulation, signed offline starts, and Node replay worker are also superseded. Host suitability and a few operational details remain to be verified. See the [technical decision register](technical-decisions.md), [technology stack](technology-stack.md), and [infrastructure plan](infrastructure-and-operations.md).

## 1. Components and boundaries

Backend/frontend code and tests are under `source/`; English documentation is under `docs/`; GitHub Actions workflows are under `.github/workflows/`; Kubernetes/Ansible assets are under `k8s/`. Root `scripts/` is optional. The .NET solution has `Domain`, `Application`, `Infrastructure`, and `WebApp` projects. `Domain` contains the authoritative 20-year game rules, state transitions, score calculation, and ranking invariants. It accepts explicit ruleset/content version, state, player choice, and deterministic random input; it returns the next state and a report. It has no HTTP, EF Core, wall-clock, or global-random dependency. Integer PLN and fixed-point/rational arithmetic keep results reproducible. `Application` implements CQRS use cases and Wolverine handlers. `Infrastructure` implements EF Core/SQL Server persistence, Identity, secret hashing, and external adapters. `WebApp` hosts WolverineFx.Http endpoints, authorization, OpenAPI and dependency wiring. The exact proposed tree and package choices are in [Technology Stack](technology-stack.md).

The React 19.3.0/Vite application renders choices and reports and keeps transient interface state. It does **not** compute career outcomes. A private Node replay worker and .NET WebAssembly runtime are not required. If an action must be audited or recomputed, the server can replay its own event log through the same C# `Domain` ruleset and its immutable event/balance snapshot. Retain old ruleset implementations and published content/configuration snapshots for careers started before an update; a new career starts on the current published version. Test old-version loading before removing any ruleset. The ruleset ID and content/balance version are immutable per career.

Wolverine is used for in-process commands, queries and HTTP endpoints. The owner chose no durable Wolverine queues at launch. Ordinary actions settle in one server transaction. If a 52-week auto batch cannot finish comfortably within an HTTP request, a persisted application job and bounded hosted worker may process it; this does not introduce a message broker. Keep endpoint classes thin, with explicit request/response DTOs and FluentValidation. Use ASP.NET Core [rate limiting](https://learn.microsoft.com/en-us/aspnet/core/performance/rate-limit?view=aspnetcore-10.0) and Problem Details. [Wolverine HTTP](https://wolverinefx.net/guide/http/), [Wolverine HTTP validation](https://wolverinefx.net/guide/http/validation).

## 2. Online play, anonymous access and saves

An active connection is required to create a career, read its current state, make a weekly choice, resolve a live event, run an auto batch, load a save, and receive a result. When disconnected or the API is unavailable, the UI shows the last confirmed report and a clear `Connection required` state. It never offers an unconfirmed choice as if it had settled. PWA installation remains optional, but its cached shell is only an entry point and outage explanation; it does not promise offline gameplay. A service worker may cache static assets for speed and installability. A ranking service outage also blocks active play because the game engine and career database are server-side.

Public players do not create Identity accounts. In the target M4 recovery flow, career creation issues a high-entropy anonymous career secret and a recovery key **specific to that career**. The browser may index several locally known careers, but each has separate access material; recovering one does not unlock any other. The browser stores each secret locally and the user can export or copy each recovery key to restore that career on another device; the server stores only verifiers/hashes, never raw secrets. A career request proves possession of its own secret. A recovered session can rotate browser access without changing career state. Show the recovery key clearly at creation and warn that a lost browser secret and lost recovery key cannot be restored by a username, since none exists. Rate-limit recovery attempts and redact secrets from logs, analytics, URLs and support screenshots. M2 sends the career secret (32 random bytes, base64url) as `Authorization: Bearer`; the server stores only its SHA-256 and answers an unknown career and a wrong secret alike with `404 career-not-found` (TD-92). The recovery-key format is an implementation detail to test before release.

**M2 creation safety (TD-105, TD-106):** Before `POST /v1/careers`, the client checks that this browser can save the returned secret and blocks creation if it cannot. The create endpoint has no idempotency key, so a network failure does not automatically retry the POST. A response lost after the server creates a career can still leave its secret unavailable; a later recovery or idempotent-creation design must address that case ([#64](https://github.com/adamcharusta/PolskiStreamerSimulator/issues/64), M4).

The server autosaves each settled step and completed week transactionally. A request includes a unique idempotency key and the last observed state version. If a connection drops after the server commits, the client reloads the career or repeats the **same** command ID to get the committed result; it never draws a different random outcome. Concurrent tabs cannot advance one career from the same version: one succeeds, the other receives a conflict and refreshes. A 4/13/52-week batch commits complete weeks and stops before a mandatory player decision; its progress and last committed week are queryable after reconnect. **Implemented in M2 (TD-90):** the 13-week batch commits each week on its own; a repeat with the same command ID returns the stored weeks or finishes a batch that crashed, and never plays weeks after the career moved on; concurrent repeats of one batch store each week once and answer alike (TD-97). A batch must never silently skip a weekly action or reroll a settled week.

The owner retained **three manual save slots and export/import for unranked careers only**. An unranked slot is a server-side snapshot with its own version and display metadata; restoring it branches or rewinds only an unranked career. An exported unranked save is a versioned data file that the server validates on import; imported state is permanently unranked. Ranked careers are append-only: no manual slot, import, rollback, or duplicate branch can affect their score. The UI explains this before a career starts. A player can still view ranked history and export a final diploma. `pdf-lib` generates that diploma locally from the server's final, read-only report. The exact unranked slot semantics and export format need implementation tests and a storage estimate.

## 3. Ranked career protocol

A ranked career starts through the online API with background, difficulty and the current season/ruleset selected before the first week. The server records every legal choice, random draw, weekly action, outcome and resulting state. The client sends **choices**, not calculated followers, money, rolls or final score. The C# `Domain` computes odds and outcomes. When presenting a chance before a choice, the API returns the current legal options and their odds for a specific career version; at submission it recomputes legality against that version. The weekly report gives the roll and explanation after resolution.

No signed offline start or three-starts-per-day quota remains. General rate limits and abuse detection still protect career creation and expensive batch requests without imposing that removed gameplay limit. The anonymous secret authorizes access to a career but does not grant administrator rights. At the career ending, the server calculates the score from authoritative state, freezes the final record and accepts a 1–5-character arcade nickname for the season's leaderboard. It can recompute the career from its server event log for audit or integrity checks, but the browser does not submit a trusted replay log. Only the highest 100 eligible scores are shown for a season; verified historical entries remain stored for receipts and moderation.

The online model removes the earlier offline retry/anti-cheat limitation: players cannot locally rewind ranked server state or submit a fabricated outcome. It does not prove that a human played, and rate limits plus outlier review are still appropriate. A player's ranked state and nickname remain under server control. Publishing a score is idempotent by career ID; repeated calls return the existing result. If an outage overlaps the season submission deadline, the owner announces a new server-side deadline for **every eligible career in that season**. The server enforces the published timestamp uniformly. The standard old-season window remains 90 days after close unless such an extension is announced.

### Proposed public API

| Endpoint | Purpose | Key behavior |
| --- | --- | --- |
| `POST /v1/careers` | Start ranked or unranked career | Returns career ID, first state version and one-time recovery material. **Implemented in M2 (TD-92):** unranked only, returns the career secret once; recovery material follows later. |
| `GET /v1/career-options` | Character-creation choices | **Implemented in M2 (TD-101):** no secret; the starting profile of each background and the score multiplier of each difficulty from the current content, so the client shows real numbers without duplicating content. |
| `GET /v1/careers/{id}` | Resume a career | Requires anonymous career secret; returns current state and legal next step. **Implemented in M2:** the view carries the next step with its plans or the current event and its odds, bound to the state version, so the separate `…/choices` endpoint was merged into it (TD-92). |
| `POST /v1/careers/{id}/actions` | Settle one decision/week | Requires idempotency key and expected version; server computes outcome. **Implemented in M2:** steps `startWeek`, `resolveEvent`, `settleWeek`; **M3-A (PR 3):** the next step can also be a mandatory decision and the action list gains `resolveDecision`; a queued decision is answered before `planWeek`, and the wrong step returns `409` (`decision-pending`, `no-pending-decision`); event and choice text is sent as ICU strings from the career's pinned content snapshot and formatted in the browser (TD-111, TD-116); a repeated command ID returns the stored result, a different body under it returns `422 command-id-reused` (TD-91, TD-92). **M3-B (PR 4):** `startWeek` also takes `wager` (`low`, `medium`, `high`) and `targetPlatform`; the free command `respondOffer` (`offerId`, `accept`; log kind `RespondOffer`) answers a sponsor offer between weeks, also while decisions are queued, never as a main action and never as a batch pause, and is refused as `illegal-action` (`week-in-progress`, `unknown-offer`, `contract-limit`, `same-sponsor`, `prerequisite:<name>`). The career view adds the platform and its start week, active strikes, banned platforms, offers with every term and the reason an acceptance would be refused, deals and the side business; each plan option adds the wager terms, policy exposure, migration estimate and sponsor consequences; report views add the strike roll, the wager and a platform move. The `platform-ban` decision is built by the ruleset, not read from content, and the view takes its definition from the presentation. New request fields are omitted from stored JSON when null and stored responses written before PR 4 read with the M3-A defaults (TD-91, TD-117). |
| `POST /v1/careers/{id}/batches` | Simulate 4, 13 or 52 weeks | Uses saved policy; stops at mandatory decisions and exposes committed progress. **Implemented in M2 (TD-90, TD-92):** 13 weeks only, played by the fixed `Balanced` policy with a reason for every decision; the result lists each week, a summary and the stop reason (`completed`, `pausedForDecision`, `careerEnded`, `interrupted`). |
| `POST /v1/careers/{id}/saves` | Create or restore an unranked slot | Rejected for ranked careers. |
| `POST /v1/careers/recover` | Recover access from exported key | Rate-limited; rotates browser credential after proof. |
| `POST /v1/careers/{id}/leaderboard-entry` | Publish final score with nickname | Ranked, ended careers only; idempotent. |
| `GET /v1/leaderboard?season=current&limit=100` | Read public top 100 | Season-scoped and cached; only public score fields. |
| `GET /v1/seasons` | Read seasons and deadlines | Includes announced deadline extensions. |

The owner-only `/admin` API is a separate authorization area within `WebApp`. Wolverine endpoints use ASP.NET Core Identity cookie authentication with TOTP/recovery-code 2FA and an owner policy; all mutating cookie-authenticated endpoints require anti-forgery protection. The React `/admin` route uses the same Tailwind/shadcn/ui system as the game and is lazy loaded. Hiding the route is a UI choice; API authorization is the boundary. Public players have no accounts or registration endpoint. The admin API supports event draft CRUD, balance-constant draft edits, preview/validation, publication and history alongside leaderboard moderation. [Wolverine authorization](https://wolverinefx.net/guide/http/security), [ASP.NET Core Identity](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity?view=aspnetcore-10.0).

## 4. SQL Server data, moderation and operations

M2 implements `careers`, `career_secrets`, `career_actions` (with a `step` per batch week and the week report as JSON) and `content_snapshots` (both content files byte-for-byte under their digest) in schema `game` (TD-91). Proposed SQL Server tables include `careers` (ID, ruleset, season, published content/balance version, ranked flag, state/version, last successful gameplay action, ending), `career_actions` (career ID, sequence, command ID, choice, deterministic draw/result, resulting hash), `career_secrets` (career ID, hash/rotation metadata), `unranked_save_slots` (career ID, slot, snapshot/version), `seasons` (opening, closing and submission deadline), `rulesets`, event and balance drafts, immutable published event/balance snapshots with digests, `leaderboard_entries`, Identity tables, moderation/configuration audit and operational logs. A unique `(career_id, command_id)` constraint makes retries idempotent; a row-version check prevents conflicting advances. Index leaderboard by season and score with stable tie breakers. Retain published snapshots for old careers and verification. Keep large reports and action logs under an explicit retention and capacity plan; active ranked careers need enough history for audit and recovery.

Delete an **unfinished career** after six calendar months without a successful gameplay action. Reading a career, visiting the home page, or repeatedly retrying a duplicate command does not reset this clock. Show the rule and the last-action/expiry date in the UI; a recovery key cannot restore a deleted career. Purge its access material, unranked slots and action records together. Retain a **finished career and its detailed history for 12 calendar months after the ending**, then purge its private state, access material and action records. Keep season leaderboard results indefinitely as separate minimal records containing public score fields and the necessary moderation receipt; public results must not depend on the deleted career row. Show the finished-career expiry date before the player loses access to diploma generation or detailed history. Deleted data may remain in encrypted historical backups until those backups expire under the 30-daily/12-monthly policy. As a proposed restore procedure, rerun the retention sweep against restored data before reopening the API; this prevents an older backup from reviving expired careers in active service.

The owner-only admin panel can hide abusive nicknames, revoke an invalid entry, inspect verification and health status, announce a season deadline extension, manage event drafts, and edit balance constants. Every moderation, content, balance or deadline change writes an independent transactional audit record with actor, reason, timestamp and old/new values. Serilog SQL events are operational diagnostics and must never be the sole audit trail. Public leaderboard responses expose no anonymous secret, recovery key, IP address or action log. The nickname policy is 1–5 visible characters after normalization, with a restricted supported alphabet and plain-text rendering; rejected names can be changed without losing an ended career.

Seed the first event catalog and balance constants from versioned repository data, then let the owner maintain **drafts** in SQL Server through `/admin`. The panel can add, edit and delete unpublished event drafts; published versions are immutable and can only be archived from future releases. Balance constants are named, typed and bounded values consumed by C# `Domain`, not arbitrary code or formulas entered in the browser. Before publishing, validate the full event graph and parameter ranges, preview the diff and representative outcomes, and run deterministic simulations/regression checks on the candidate snapshot. Publication atomically records an immutable content/balance version and makes it available to **new** careers; existing careers stay pinned to their original version. Any change to event availability, eligibility, probability, effects or numeric balance starts a new leaderboard season. Text-only corrections may publish a new content revision without a new season, while preserving old text for pinned careers. A change requiring new effect types or game rules goes through the tested C# deployment pipeline. Record who published what and allow reversal by copying a prior snapshot into a **new** publication (and a new season when mechanics differ), never by rewriting a snapshot already in use. Export published snapshots and digests for recovery and reproducible audits.

The owner chose daily SQL Server backups to the separate VPS at SSH alias `ovh2`, retaining **30 daily and 12 monthly** copies and periodically restoring from that host. Encrypt before transfer, verify integrity, alert on failed transfer or missed backup, and prune only after a newer valid backup exists. The owner explicitly accepts a launch recovery-point target of approximately **24 hours of online ranking and career data**, meaning that a severe database failure can lose roughly a day of career progress or an entire career created since the last backup. The distinct recovery-time target is to restore service within **24 hours** of an outage. These are operational targets, not guarantees. Player-facing outage and recovery copy must explain potential progress loss plainly. Send backup and service-outage alerts to the owner through a private Discord destination, without player data or secrets. Test both failure and recovery notifications. [SQL Server backup and restore guidance](https://learn.microsoft.com/en-us/sql/linux/business-continuity/backup-restore/database-backup-restore?view=sql-server-ver17).

Keep signing/credential keys and SQL passwords outside source control; rotate them without invalidating active careers unnecessarily. Serilog writes to console and a bounded SQL log table. Console logging must work during SQL outages; SQL sink batches are not guaranteed audit records. Define log retention and SQL capacity before launch. Identity, career access and staging secrets are separate. Gameplay analytics remain off unless the player grants revocable consent; never include career secrets, full saves or raw action logs. Publish privacy/retention notices before enabling analytics.

## 5. Deployment and release

The proposed game host is the owner's VPS at SSH alias `ovh`; `ovh2` remains outside k3s as the off-host backup server. Two read-only SSH inventory attempts on 2026-10-12 timed out during banner exchange, and the owner deferred further host checks. Before deployment, verify CPU architecture, RAM/disk headroom, current services, k3s/ingress state, persistent-storage suitability and `ovh2` backup capacity without disturbing other workloads. A new shared SQL Server instance is required in the `database` namespace, as a single-replica StatefulSet with a private Service and PVC. SQL Server 2025 Express is a candidate only if host resources and [edition limits](https://learn.microsoft.com/en-us/sql/sql-server/editions-and-components-of-sql-server-2025?view=sql-server-ver17) fit; check the [Linux requirements](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-setup?view=sql-server-ver17). Developer edition is not a production substitute. [Microsoft StatefulSet guidance](https://learn.microsoft.com/en-us/sql/linux/containers/kubernetes-best-practices-statefulsets?view=sql-server-ver17).

Ansible-managed k3s replaces production Docker Compose. Use `streamer-prod`, `streamer-rc` and `streamer-staging` namespaces for the app and separate `database` and `vault` namespaces for reusable SQL Server and HashiCorp Vault. Helm manages the shared services and game workloads, with Ansible checking and orchestrating their configuration. Inspect the host's existing ingress; k3s packages Traefik by default, so avoid installing a second public proxy without a reason. Serve the React build and `/v1/*` API on the production `polskistreamersimulator.pl` origin through HTTPS. `staging.polskistreamersimulator.pl` remains accessible only to invited testers; the release-candidate origin `rc.polskistreamersimulator.pl` is likewise restricted. Protect the entire non-production origins, including API and admin paths, with individual tester credentials or an equivalent gate. Separate production, release-candidate and staging databases, service identities, Vault policies and application secrets. No replay-worker or browser-WASM container is part of the current architecture. The detailed plan, including Metrics Server/HPA, storage and Vault recovery, is in [Infrastructure and Operations](infrastructure-and-operations.md).

The public GitHub repository runs CI: build React and .NET, generate OpenAPI and Orval code, test deterministic domain transitions and EF Core/Identity with xUnit/Testcontainers, run Vitest/Testing Library and Playwright flows, then build immutable images. Daily work follows Git Flow: `feature/*` and `bugfix/*` feed `develop`; a passing `develop` push deploys staging after Ansible conformity checks. A `release/*` branch creates a versioned candidate in a separate environment. A tested PR merge from `release/*` into production `main` runs checks for that exact commit and deploys it through Kubernetes automatically. Urgent `hotfix/*` branches from `main`, reaches `main` by tested PR, then is reconciled into `develop` and any open release. Ansible drift blocks and reports any deployment; a separate infrastructure workflow repairs it. The earlier manual approval inside the production workflow is superseded; merging the release/hotfix PR is the release decision. Rehearse app rollback, SQL and Vault restore, and old-ruleset compatibility. A material balance change starts a new leaderboard season; existing careers keep their original ruleset. The local development stack uses Docker Compose, while deployed environments use k3s. See [Development and Delivery](development-and-delivery.md).

## 6. Security and product constraints

Serve only over HTTPS, validate every request and imported unranked save, enforce body-size and rate limits, use parameterized EF Core queries, apply a content security policy, and render nicknames/localized content as text. Admin cookie login requires 2FA and anti-forgery protection; a public career secret is a separate bearer credential with career-only scope. The age confirmation is a user assertion, not proof of age. Obtain region-specific review of adult themes, simulated gambling, privacy notice, ranking names and data retention before public launch. This document does not claim legal compliance.

The visible game flow remains Polish and accessible by keyboard and on phones. During API downtime, show a connection-required explanation and the most recent confirmed state if cached; do not accept speculative offline moves. The regular browser page works without PWA installation, but **both require a live connection to play**.
